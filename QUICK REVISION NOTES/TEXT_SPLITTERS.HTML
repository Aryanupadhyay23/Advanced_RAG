Text Splitters

Chunking strategies for RAG – breaking documents into embedding‑friendly pieces while preserving semantic coherence.

1. Core Idea

  • What is a text splitter? A component that divides a long document into smaller, self‑contained chunks so that each chunk can be embedded and retrieved effectively. It’s the bridge between document loading and vector indexing.
  • Why is it needed? LLMs have a context window limit; embedding models work best on short, focused text. Splitting ensures each chunk fits within the model’s limits and carries a coherent piece of information.
  • Key trade‑off: Chunk size – too large: exceeds context window, dilutes relevance. Too small: loses context, splits sentences/ideas mid‑way, leading to poor retrieval.
  • Core parameters: chunk_size (target length), chunk_overlap (how much adjacent chunks share to preserve continuity), length_function (character‑based or token‑based).

2. Mental Model

🔹 The “Encyclopedia Slice”

You have a massive encyclopedia. You can't read it all at once, so you cut it into cards (chunks). Each card should contain a complete idea (a paragraph or section) so that when you search for “rainfall”, you get a card about rain, not half a sentence about rain and half about sunshine.

🔹 The “Sliding Window Over Text”

Imagine a sliding window that moves across the text by a fixed step size. The window captures a chunk, then slides forward by (chunk_size – overlap), ensuring that the last few sentences of one chunk reappear at the start of the next – preserving continuity for nearby chunks.

3. Key Concepts

ConceptDescriptionImportance
Chunk SizeThe target number of characters (or tokens) per chunk. The splitter tries to keep chunks near this limit while respecting natural boundaries.Directly affects retrieval granularity. Too large → noisy context; too small → fragmented meaning.
Chunk OverlapThe number of characters (or tokens) shared between consecutive chunks. Creates a buffer zone so that context across chunk boundaries is not lost.Prevents splitting an entity or fact exactly at the boundary; improves retrieval recall.
Length FunctionHow the chunk length is measured – most commonly len() (character count) or a tokenizer‑based function (e.g., tiktoken token count).Token‑based splitting is more accurate for LLM context windows; character‑based is simpler and faster.
SeparatorsA list of characters/strings used to find natural break points. The splitter tries to split in order: paragraph (\n\n), sentence (., ?, !), word ( ), character.Maintains linguistic coherence; avoids breaking mid‑word or mid‑sentence unless necessary.
Semantic SplittingUse embeddings and similarity thresholds to detect topic shifts and split at those boundaries, creating chunks that represent distinct subtopics.Produces more meaningful chunks than fixed‑size splitting, but is computationally heavier.

4. Types of Text Splitters

SplitterHow It WorksBest ForExample (LangChain)
Recursive Character Text Splitter Recursively splits text using a hierarchy of separators: double newline, single newline, space, empty string. Tries to keep chunks below chunk_size by splitting at the most semantic boundary first. General‑purpose documents; preserves paragraphs and sentences. RecursiveCharacterTextSplitter
Token Text Splitter Uses a tokenizer (e.g., tiktoken for OpenAI models) to count tokens and split based on token count, not characters. When precise token limits are critical for the target LLM. TokenTextSplitter
Markdown Header Text Splitter Splits a Markdown document by headers (H1, H2, H3…) and attaches header information as metadata to each chunk. Chunks are kept together under a header until the size limit. Structured documentation, READMEs, wikis. MarkdownHeaderTextSplitter
HTML Section Splitter Parses HTML and splits by tags (e.g., <section>, <article>, headings) while preserving the document structure. Web‑scraped content, technical documentation. HTMLHeaderTextSplitter
Code Text Splitter Language‑aware splitter for code (Python, JS, etc.) that respects syntax – splits by functions, classes, and logical blocks. Code repositories for code‑generation or code‑explanation RAG. RecursiveCharacterTextSplitter.from_language()
Semantic Splitter Computes embeddings for sentences, then groups them into chunks by detecting significant drops in cosine similarity between consecutive sentences. Requires an embedding model. Long, unstructured documents with topical shifts. SemanticChunker (LangChain experimental)

7. Common Challenges & Mitigations

ChallengeDescriptionSolution
Splitting mid‑entityA critical fact (e.g., “Machine Learning course is 8 weeks”) gets split across two chunks, making each chunk incomplete.Use overlap; increase overlap to at least 50% of the expected fact length. Consider semantic splitting.
Table / list disruptionTables lose structure when split; a row may be separated from its header.Use a table‑aware splitter or pre‑process tables into markdown/CSV. Attach table header as metadata or prepend to each chunk.
Large chunk exceeding model limitA single paragraph or code block is too long and cannot be split without losing meaning.Allow chunk_size overflow with a hard maximum; use summarization for very large blocks.
Inconsistent chunk sizesSome chunks are very small (e.g., just a title or a single line), leading to noisy embeddings.Filter out chunks below a minimum token count (e.g., min_chunk_size=20).
Multilingual textSeparators (e.g., ". ") may not work for languages with different punctuation (e.g., Chinese, Japanese).Use language‑specific splitters or regex‑based separators. Token‑based splitting with a multilingual tokenizer is robust.

9. Interview Questions

Q1: Why is text splitting necessary in a RAG pipeline?

A: Because raw documents are too long for embedding models (which have token limits) and for LLM context windows. Splitting breaks them into manageable, searchable chunks that retain local context and can be independently embedded and retrieved.

Q2: Explain the difference between character‑based and token‑based splitting.

A: Character‑based splitting measures length by the number of characters (using len()), while token‑based uses an actual tokenizer (like tiktoken) to count tokens, which is more aligned with how LLMs process text. Token‑based is more accurate for staying within context windows.

Q3: What is the role of overlap in text splitting? Can overlap ever be harmful?

A: Overlap ensures that information near chunk boundaries is duplicated in adjacent chunks, preventing a query from missing a fact that was split. It can be harmful if it causes the same fact to dominate multiple retrieval results (redundancy), or if it significantly increases the number of chunks (cost). Optimal overlap is usually 10–20% of chunk size.

Q4: When would you choose a semantic splitter over a recursive character splitter?

A: When the document has clear topic shifts and you want chunks that represent coherent subtopics. Semantic splitting uses embedding similarity to detect breaks, producing thematically focused chunks. It’s useful for long, unstructured text like research papers or articles. It’s more expensive, so it’s not the default choice.

Q5: How would you handle a table that spans multiple chunks in a PDF document?

A: First, try to extract the table as a separate entity (e.g., using a table parser) and convert it to a text representation (markdown, CSV) with the header prepended. If it must be split, ensure each chunk includes the table header by storing it in metadata or prepending it. Using overlap can also help preserve rows at boundaries.

10. Common Mistakes

❌ Wrong Practice✅ Correct Approach
Using chunk_size=0 or no overlap.Always set a positive overlap (10‑20%). Zero overlap risks splitting important context at every boundary.
Ignoring the chunk size limit of the embedding model (e.g., 8191 tokens for ada‑002).Set chunk_size safely below the embedding model’s maximum input length; consider both chunk and expected query length.
Splitting purely by character count without respecting sentence boundaries.Use recursive character splitter with a hierarchy of separators, or semantic splitting, to keep linguistic units intact.
Applying the same splitter to code, Markdown, and unstructured text without customization.Use language‑aware or structure‑aware splitters for code (respecting functions) and Markdown (respecting headings).
Not filtering out very small chunks (e.g., a single punctuation mark).Set a minimum chunk length (e.g., 10 tokens) to remove noise and improve retrieval quality.

11. Exam Cram Facts (Day‑Before Revision)

  1. Text splitters convert long documents into smaller, overlapping chunks for embedding and retrieval.
  2. Key parameters: chunk_size (target length), chunk_overlap (10–20% of size), length_function (chars or tokens).
  3. RecursiveCharacterTextSplitter: splits by paragraph, then sentence, then space, then character.
  4. TokenTextSplitter uses a tokenizer (tiktoken) to measure length, aligning with LLM limits.
  5. MarkdownHeaderTextSplitter preserves hierarchy and attaches header metadata to chunks.
  6. Semantic splitter uses embeddings to detect topic shifts – coherent but computationally heavy.
  7. Overlap prevents splitting of a single fact across chunk boundaries; typical overlap = 10‑20%.
  8. Chunk size is a trade‑off: larger = more context, smaller = more precise retrieval.
  9. Always filter out excessively small chunks; set a minimum size to reduce noise.
  10. For production, use token‑based splitting to accurately respect the LLM’s context window.
