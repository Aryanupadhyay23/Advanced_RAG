Multimodal RAG

Unstructured Loaders, Embedding Strategies, the Representation & Retrieval Problem, and CLIP — Complete Revision Sheet

1. What is Multimodal RAG?

Multimodal RAG extends standard text-only RAG so the knowledge base can contain mixed content types — text, tables, and images (charts, diagrams, scanned pages, photos) — and the pipeline can retrieve and reason across all of them to answer a user's query.

  • Why it exists: Real-world documents (PDFs, slide decks, manuals) are rarely pure text — they contain figures, tables, and screenshots that carry critical information a text-only RAG would silently ignore.
  • Core challenge: Text embeddings are built for language; images are pixels, not tokens — so the pipeline needs new components to load, represent, and retrieve non-text content.

2. Unstructured Document Loader

Before any embedding happens, raw files (PDF, PPTX, DOCX, HTML, scanned images) must be parsed and decomposed into distinct content elements. This is the job of an unstructured document loader (e.g., the unstructured library, LlamaParse, Azure Doc Intelligence).

  • What it does: Walks through a document and classifies/extracts each region into typed elements — Title, NarrativeText, Table, Image, FigureCaption, ListItem, etc.
  • Why "unstructured": Source documents have no fixed schema — the loader must infer structure (layout detection, OCR, table detection) rather than parse a known format.
  • Output: A list of elements, each tagged with its type, page number, bounding box coordinates, and raw content (text string OR extracted image bytes/path).

Step-by-Step: Loading a Mixed PDF

  1. Layout Detection: A vision-based layout model (e.g., Detectron2-based) segments each page into regions: text blocks, tables, figures/images.
  2. Text Extraction: For text regions, extract raw text directly (or OCR if scanned) → produces text chunks.
  3. Table Extraction: Tables are extracted preserving row/column structure (often converted to HTML/Markdown for LLM readability).
  4. Image Extraction: Figures/images/charts are cropped out and saved as separate image files, linked back to their page + surrounding text (captions, nearby paragraphs) for context.
  5. Chunking: Text elements are grouped into RAG-sized chunks; each image is kept as its own retrievable unit (often paired with its caption/context text).

3. Embedding Models in Multimodal RAG

In text-only RAG, one embedding model turns every chunk into a vector in a shared space, so cosine similarity between the query vector and a chunk vector = relevance. In multimodal RAG, this breaks down the moment images enter the knowledge base — text embedding models have no concept of pixels.

Why Standard Text Embeddings Fail on Images

  • A text embedding model (e.g., OpenAI text-embedding-3, BGE, E5) is trained ONLY on token sequences — it has no input pathway for raw pixel data.
  • You cannot cosine-similarity-compare a text query vector against an image unless the image is somehow projected into the same vector space as the text.
  • This gap is exactly what creates the two central problems of multimodal RAG (detailed on Page 3).

4. The Two Core Problems of Multimodal RAG

Once a loader extracts images from a document, two distinct, sequential problems must be solved before an image can ever be used to answer a query:

#ProblemQuestion it Asks
1Representational ProblemHow do we turn an image into an embedding (a vector) at all?
2Retrieval ProblemOnce we have that embedding, how do we similarity-search it against a text query — and once retrieved, how do we actually get the image (or its information) into the LLM's context to generate an answer?
🧠 Memory Hook: "Represent, then Retrieve" — Problem 1 is about CREATING the vector; Problem 2 is about USING that vector (searching it + feeding the underlying content to the LLM).

Problem 1 — Representational Problem (Detail)

  • An image is a grid of pixel values (H × W × 3 channels) — fundamentally different data type from a token sequence.
  • We need a function f(image) → vector ∈ ℝᵈ such that semantically similar images/concepts land close together in vector space.
  • Ideally, this vector space should ALSO be comparable to text vectors, so a text query like "a red sports car" can match an image of a red sports car.

Problem 2 — Retrieval Problem (Detail)

  • Even with image embeddings computed, you must decide: search text query against image vectors directly? Or convert everything to one modality first?
  • Context-injection sub-problem: After the correct image is retrieved (its vector matched the query), the raw image itself must somehow reach the LLM so it can actually "see" it and use it to generate the answer — this requires either (a) passing the raw image to a vision-capable LLM at generation time, or (b) having already converted the image to a textual description that gets inserted into the prompt like normal text context.
  • This is why multimodal RAG pipelines need a clear strategy for BOTH embedding AND final context delivery — solving Problem 1 alone is not enough.
Interview Trap: Students often think "embed the image" solves multimodal RAG. It only solves retrieval matching (Problem 2's search step) — you still need a separate mechanism to get the actual visual information into the LLM's context window at generation time.

5. Solving the Two Problems — Two Strategies

Strategy 1: Vision-Capable LLM → Caption → Text Embed

Idea: Don't embed the image directly at all — use a vision-capable LLM (e.g., GPT-4V, Claude, Gemini) to describe the image in detailed natural language, then embed that description using an ordinary text embedding model, alongside the rest of the text chunks.

  1. Extract image from the document (via unstructured loader).
  2. Caption it: Feed the image to a vision LLM with a prompt like "Describe this image/chart/diagram in detail, including any text, labels, numbers, and trends visible."
  3. Generate detailed text description — this becomes a proxy document for the image.
  4. Embed the description using the SAME text embedding model used for the rest of the corpus → now it lives in the same vector space as all text chunks.
  5. Store: Save {description embedding vector, original image reference} so that at retrieval time, if the description matches the query, you can pull up either the description text OR the original raw image to inject into the LLM's context.
ProsCons
Simple — reuses existing text embedding + text RAG infra unchangedLossy — captioning compresses/loses visual detail (exact chart values, fine layout, subtle visual cues)
Works with ANY text embedding model, no special training neededExtra LLM call per image = slower indexing, added cost
Retrieval quality benefits from mature text embedding modelsQuality bottlenecked by captioning LLM's descriptive accuracy/detail

Strategy 2: Multimodal Embedding Model (Direct Image Embedding)

Idea: Use a single embedding model trained to accept BOTH text and images as input and project both into one shared/joint vector space — generate the image's embedding vector directly from pixels, no captioning step required. CLIP is the canonical example.

  1. Extract image from the document (via unstructured loader).
  2. Feed the raw image directly into the multimodal embedding model's image encoder → outputs a vector in the shared embedding space.
  3. Text queries are fed into the SAME model's text encoder → also outputs a vector in that SAME shared space.
  4. Similarity search: Because both vectors live in the same space, cosine similarity between a text query vector and an image vector is directly meaningful — no intermediate text conversion needed.
  5. Context delivery: Once the right image is retrieved, either pass the raw image to a vision-capable LLM at generation time, or (optionally) generate a caption at that point (only for the retrieved image, not the whole corpus) to inject as text.
ProsCons
No information loss at indexing time — raw visual signal is embedded directlyRequires a specialized multimodal embedding model (CLIP, SigLIP, etc.)
Single encoder pass per image — often faster/cheaper than an LLM captioning callJoint embedding spaces can be less precise for fine-grained text-heavy content (e.g., dense tables) vs a dedicated text model
Enables true cross-modal search (image-to-image, text-to-image, image-to-text)Still need a separate step to get the actual image INTO the LLM's context at generation time

7. CLIP (Contrastive Language–Image Pretraining)

CLIP (OpenAI) is a dual-encoder model — one image encoder (typically a Vision Transformer or ResNet) and one text encoder (a Transformer) — trained so that matching (image, caption) pairs are pulled close together in a shared embedding space, and non-matching pairs are pushed apart.

Architecture (Dual Encoder)

Image → Image Encoder (ViT/ResNet) → Image Embedding
Text → Text Encoder (Transformer) → Text Embedding

Both encoders project into the SAME dimensionality (d) shared space, then embeddings are L2-normalized so cosine similarity = dot product. This shared, normalized space is what makes cross-modal search possible.

8. Contrastive Learning — In Detail

Contrastive learning is a self-supervised training paradigm where the model learns representations by contrasting positive pairs (things that should be similar) against negative pairs (things that should be dissimilar) — instead of learning from explicit class labels.

Core Idea (Step-by-Step)

  1. Positive pair: An image and its correct/matching caption (e.g., a photo of a dog + the text "a photo of a dog") form a positive pair — the model should embed them close together.
  2. Negative pairs: Every other mismatched (image, caption) combination in the training batch is treated as a negative pair — the model should push these apart.
  3. Batch construction: Take a batch of N (image, text) pairs scraped from the internet (CLIP used ~400 million pairs). Within one batch, there are N correct matches (diagonal) and N² − N incorrect combinations (off-diagonal).
  4. Encode: Pass all N images through the image encoder → N image embeddings. Pass all N texts through the text encoder → N text embeddings.
  5. Similarity matrix: Compute the cosine similarity between EVERY image embedding and EVERY text embedding → an N × N similarity matrix.
  6. Contrastive objective (InfoNCE-style loss): For each image, treat its true matching caption's similarity score as the "correct class" among all N captions in the batch, and apply cross-entropy loss — this pulls the diagonal (correct pairs) similarity up and pushes off-diagonal (incorrect pairs) similarity down. This is done symmetrically: once treating images as the anchor (image→text loss) and once treating text as the anchor (text→image loss).
  7. Backpropagate through both encoders jointly — over millions of batches, the model learns a shared space where semantically aligned image-text pairs are close and everything else is far.
CLIP Contrastive Loss (Symmetric InfoNCE)
$$ \mathcal{L} = \frac{1}{2}\left( \mathcal{L}_{\text{image} \to \text{text}} + \mathcal{L}_{\text{text} \to \text{image}} \right) $$ $$ \mathcal{L}_{i \to t} = -\frac{1}{N}\sum_{i=1}^{N} \log \frac{\exp(\text{sim}(I_i, T_i)/\tau)}{\sum_{j=1}^{N}\exp(\text{sim}(I_i, T_j)/\tau)} $$
N = batch size (number of image-text pairs)
Ii, Ti = embedding of the i-th image and its TRUE matching text
sim(·,·) = cosine similarity between two embeddings
τ (tau) = learnable temperature parameter controlling how "sharp"/confident the similarity distribution is
Lt→i = same formula computed the other direction (text as anchor, image as candidates)
🧠 Memory Hook: "Musical chairs for embeddings" — in each batch, every image must find its one true caption among N candidates (and vice versa); loss rewards correctly picking your partner and rejecting everyone else's.
Interview Insight: CLIP requires NO manual class labels — it exploits naturally occurring (image, alt-text/caption) pairs from the web at massive scale, making it a form of self-supervised (specifically weakly-supervised) learning, not fully supervised classification.

9. How CLIP Works Across Both Text AND Images

  • Separate encoders, shared output space: The image encoder and text encoder are architecturally different (ViT/CNN vs Transformer) — they don't share weights — but both are trained to output vectors of the same dimensionality that land in one common geometric space.
  • Alignment, not translation: CLIP doesn't "translate" images into text or vice versa — it learns to place semantically equivalent concepts (a picture of a cat AND the word "cat") at similar coordinates in that shared space.
  • Zero-shot transfer: Because of this alignment, CLIP can classify/retrieve images for concepts it never saw an explicit label for during fine-tuning — just embed candidate text labels and compare to the image embedding via cosine similarity ("zero-shot classification").
  • Symmetry enables both directions: The same shared space supports text→image search (query with text, retrieve images), image→text search (query with an image, retrieve captions), AND image→image search.

10. How CLIP Solves the Two Multimodal RAG Problems

ProblemHow CLIP Solves It
Representational ProblemCLIP's image encoder directly maps raw pixels → a dense vector — no captioning/LLM step required to "represent" the image as an embedding.
Retrieval Problem (search step)Because text and image embeddings share one space, a text query embedding can be cosine-compared DIRECTLY against stored image embeddings — genuine cross-modal similarity search.
Retrieval Problem (context-injection step)CLIP only solves the SEARCH/matching part — once the right image is found, you still pass the raw retrieved image itself to a vision-capable LLM at generation time so it can be used to construct the final answer.
Interview Trap: CLIP embeddings tell you WHICH image is relevant — they do NOT let a standard text-only LLM "read" the image's content. You must still pass the actual retrieved image to a vision-capable generator model at answer time; CLIP is a retrieval component, not a generation component.

11. Common Mistakes (❌ Wrong vs ✅ Correct)

❌ Wrong Belief✅ Correct Understanding
"Embedding the image is the whole solution to multimodal RAG."Embedding only solves retrieval matching; you still need a strategy to deliver the actual image content into the LLM's context at generation time.
"CLIP translates images into captions."CLIP aligns embeddings in a shared space — it does not generate natural language descriptions; captioning is a separate task (done by vision LLMs).
"Multimodal embedding models are always better than the caption+text-embed approach."Trade-off, not strict superiority — captioning approaches leverage mature, highly-tuned text embedding models and simple infra; multimodal embeddings preserve more visual fidelity but need specialized infra.
"CLIP needs labeled datasets like ImageNet to train."CLIP is trained via contrastive learning on naturally occurring (image, alt-text) pairs scraped from the web — no manual class labels needed.

12. Exam Cram Facts

  • Unstructured loader decomposes documents into typed elements: Title, Text, Table, Image.
  • Two core problems: (1) Representational — how to embed an image; (2) Retrieval — how to search + inject image content into context.
  • Strategy 1: Vision LLM captions image → text embedding model embeds the caption (lossy, simple).
  • Strategy 2: Multimodal embedding model (CLIP) embeds image pixels directly into a shared text-image space (high fidelity, needs specialized infra).
  • CLIP = dual encoder (image encoder + text encoder) trained via contrastive learning to align matching image-text pairs.
  • Contrastive learning = pull positive pairs together, push negative pairs apart, using a batch-wise similarity matrix + cross-entropy-style (InfoNCE) loss.
  • CLIP loss is symmetric: computed once image→text, once text→image, then averaged.
  • Temperature (τ) controls sharpness of the similarity distribution in the loss.
  • CLIP enables zero-shot classification/retrieval — no fine-tuning needed for new concepts.
  • CLIP solves search/matching, NOT final context delivery — a vision-capable LLM is still needed at generation time to actually "read" the retrieved image.

Definition: Multimodal RAG = RAG extended to retrieve/reason over text + images together.
Goal: Let a RAG pipeline use information locked inside figures/charts/scanned images, not just text.
Core Idea: Unstructured loaders extract typed elements → images need a way to become embeddings (Representational Problem) → embeddings need a way to be searched + delivered to the LLM (Retrieval Problem).

Key Formula: Loss = ½(Image→Text CE loss + Text→Image CE loss), using cosine similarity scaled by temperature τ.
Interview Trap: Embedding ≠ full solution — context delivery to a vision-capable LLM is a separate, required step.
Most Important Fact: CLIP's power comes from a SHARED embedding space, learned with NO manual labels — just naturally occurring image-caption pairs at web scale.
