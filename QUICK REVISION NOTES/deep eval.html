DeepEval

Internal Working, Synthesizer, Dataset Generation, Evaluation Pipeline & Metric Mechanics — Updated Revision Sheet

1. What is DeepEval? (Conceptual)

DeepEval is an open-source evaluation framework that applies the discipline of software testing to LLM applications. It behaves like a test harness — where each "test" is a structured record of an LLM interaction, and each "assertion" is a metric score compared against a threshold. But its true value lies in what happens internally: every metric is a small LLM-driven reasoning pipeline that decomposes natural-language output into verifiable units, judges them, and reports both a numeric score and an explanation.

  • What it is: A Python-native framework providing 50+ predefined metrics spanning RAG, agents, conversational systems, safety, and multimodal applications, plus tools to author fully custom evaluators.
  • Why it exists: LLM outputs are non-deterministic and open-ended. Traditional assertions ("did this equal that exactly?") fail completely. DeepEval replaces them with rubric-based judgments that produce reproducible scores and pass/fail signals.
  • Problem it solves: Teams need a repeatable, code-native, CI-gateable way to detect quality regressions before they reach users — covering correctness, faithfulness, relevance, safety, and agentic behaviour in one place.
  • Ecosystem relationship: DeepEval (open-source) pairs with Confident AI (a commercial platform) for dashboards, team collaboration, and production monitoring — but the framework itself remains completely free.

2. Internal Architecture — The Layers

Internally, DeepEval is organised into distinct layers, each with a clear responsibility. Understanding this layering removes the "black box" feeling when a score surprises you.

LayerResponsibility
Data LayerDefines the shapes of evaluation records — test cases, goldens, conversational threads, and datasets. Holds the raw fields the metric will read.
Metric LayerContains the scoring logic. Each metric has two responsibilities: score a single test case, and explain the score.
Judge LayerWraps the LLM used as the evaluator. Handles prompt construction, model invocation, response parsing, and retry logic.
Reasoning LayerThe techniques that structure how the judge reasons — QAG, G-Eval, DAG. This determines how a natural-language rubric becomes a number.
Synthesizer LayerGenerates synthetic goldens and datasets from source documents or seed examples — building the benchmark before evaluation runs.
Orchestration LayerCoordinates multi-step evaluation, batching, dataset iteration, concurrency, and result aggregation.
Reporting LayerProduces structured reports, pass/fail summaries, and CI-usable output — including explanations per test case.
🧠 Memory Hook: "Synthesizer builds the exam; test cases are the questions; metrics are the graders; the judge does the reasoning; the orchestrator runs the class; the reporter publishes results."

3. The Evaluation Pipeline — End-to-End Flow

Every DeepEval evaluation — whether a single assertion or a thousand test cases — follows the same internal pipeline. Each stage transforms the data into something the next stage can consume.

  1. Dataset formation (optional): If you do not already have goldens, the Synthesizer builds them from source documents or seed examples.
  2. Test case construction: For each golden, run your application to capture the actual output (or pass through the golden's expected output as a baseline check). This produces a test case per interaction.
  3. Metric preprocessing: The metric reformats the test case into the shape its reasoning technique expects — claims are extracted, questions generated, or decision graphs prepared.
  4. Judge invocation: The framework constructs a prompt from the metric's internal template plus preprocessed data, sends it to the configured LLM judge, and waits for a structured response.
  5. Response parsing: The judge returns a structured payload — typically a machine-readable list of judgments. If parsing fails, a retry is triggered up to a configured limit.
  6. Score computation: Parsed judgments are aggregated into a numeric score in [0, 1] using the metric's specific formula.
  7. Reason extraction: Alongside the score, the metric captures a natural-language explanation describing which claims passed or failed and on what grounds.
  8. Threshold check: The score is compared against the metric's threshold (or its maximum, for reverse-scaled metrics like Hallucination). The pair is marked pass or fail.
  9. Aggregation and reporting: Scores are aggregated across the dataset — mean, pass rate, worst performers — and emitted as a structured report usable in CI.
Key Internals: DeepEval's metrics are self-explaining by design — every metric returns both a score and a reason. This is not a cosmetic feature; it is a first-class part of the framework's contract, making scores auditable and debuggable rather than opaque numbers.

4. Data Structures — How Records Are Shaped Internally

Before any metric runs, the input data is packed into a standard record shape. All metrics read from this same structure, which is why any metric can be swapped for any other without changing your data preparation.

Internal Rule: Each metric declares which fields it requires. If a required field is missing or None, the metric raises a configuration error immediately — before any LLM call is wasted. This is why correct field population is the first thing to check when a metric "isn't working."

5. The Three Internal Reasoning Techniques

Almost every predefined metric is a thin wrapper around one of three reasoning techniques. These techniques determine how the LLM judge turns natural language into a score.

TechniqueInternal MechanismNumeric OutputBest For
QAGDecompose output into atomic units → generate yes/no judgments → count favourable answersRatio of favourable to totalObjective, countable properties (faithfulness, relevancy)
G-EvalRubric → chain-of-thought steps → score via weighted token probabilitiesWeighted sum across rating scaleSubjective, custom criteria (tone, coherence)
DAGTraverse a hand-built decision graph — one focused judgment per node, explicit branchingAggregated pass/fail through graphRegulated, high-stakes, auditable evaluation
🧠 Memory Hook: "QAG counts, G-Eval judges, DAG decides." QAG is mechanical; G-Eval reasons; DAG is procedural.

6. QAG — Question-Answer Generation (Internal Walkthrough)

QAG is DeepEval's workhorse technique. It powers faithfulness, answer relevancy, hallucination, and many retrieval-side metrics. Internally, QAG proceeds in four deterministic stages:

  1. Decomposition stage: The LLM breaks the target text into atomic units — individual, independently verifiable claims or statements. A single sentence like "Paris is the capital of France and was founded in 250 BC" produces two atomic claims.
  2. Question generation stage: For each atomic unit, the LLM frames a close-ended (yes/no) question designed to test whether that unit holds — answerable strictly from a designated reference source.
  3. Answering stage: The LLM answers each question using only the designated reference as ground truth. The answer is binary yes/no — no partial credit, no hedging.
  4. Aggregation stage: The metric computes the ratio of favourable answers to total answers. That ratio becomes the score.
Generic QAG Aggregation
$$ \text{Score} = \frac{\text{Favourable Judgments}}{\text{Total Judgments}} $$
Favourable = the specific pass condition for this metric
Total Judgments = count of atomic units extracted

7. G-Eval — Internal Walkthrough

G-Eval (from Liu et al., 2023) solves a different problem than QAG. QAG is great for objective checks, but subjective qualities like "tone" cannot be decomposed into countable atoms.

  1. Criteria ingestion: The user supplies a plain-language description of "good" for this metric.
  2. Auto-generation of evaluation steps: The judge LLM first generates its own chain-of-thought steps from the criteria — this is what makes G-Eval more stable than naive prompting.
  3. Step-by-step application: The LLM walks through its own generated steps against the test case.
  4. Score via token probabilities: Rather than asking for a single integer, G-Eval computes a probability-weighted score across a rating scale using the model's own output token probabilities.
G-Eval — Probability-Weighted Score
$$ \text{Score} = \sum_{s=1}^{N} s \cdot \frac{p(s)}{\sum_{k=1}^{N} p(k)} $$
s = rating value on the scale
p(s) = LLM output probability for rating token s
Result = smooth score instead of a hard single-token pick

8. DAG — Internal Walkthrough

DAG (Deep Acyclic Graph) splits a complex rubric into a graph of single-purpose decisions with explicit branching logic — trading setup effort for determinism and auditability.

  1. Graph construction (by the user): Define a directed acyclic graph where each node is one focused judgment.
  2. Entry point: Evaluation begins at a root node with a single, narrowly scoped question.
  3. Branch selection: Based on the LLM's judgment, follow a deterministic edge to the next node.
  4. Terminal nodes: Leaf nodes terminate with a pass, fail, or specific label. Score is a deterministic aggregation of the path taken.

9. The Synthesizer — Dedicated Deep Dive

The Synthesizer is DeepEval's dataset-construction engine. It is the component that turns raw source material (or a small seed set) into a fully-formed evaluation benchmark of Goldens. It is what makes DeepEval usable in projects where no curated test set exists yet — a very common situation for new LLM applications.

Internally, the Synthesizer is not a single LLM call. It is a multi-stage pipeline with its own internal reasoning steps, filtering passes, and quality guards. Understanding this pipeline is essential for judging whether a synthesized dataset is trustworthy enough to gate a deployment.

9.1 Why the Synthesizer Exists

  • Manual dataset creation is expensive: Writing hundreds of (input, expected_output, context) triples by hand is slow, error-prone, and requires domain expertise per example.
  • Golden datasets age quickly: As source documents change, the corresponding goldens must be refreshed. Regeneration by hand is impractical at scale.
  • Coverage is hard to guarantee manually: Humans tend to write similar examples in similar phrasings. A Synthesizer can deliberately vary phrasing, difficulty, and topic coverage.
  • RAG and agent systems need context-anchored examples: Goldens must reference the same documents the retriever will actually see at inference time — the Synthesizer guarantees this by anchoring every example to source chunks.

9.2 The Three Synthesis Modes (End-to-End)

  1. Ingestion stage: The Synthesizer loads source documents using DeepEval's document loaders, which parse PDFs, text files, and web pages into raw text plus metadata.
  2. Chunking stage: The document is split into overlapping passages. Chunk size and overlap are configurable. Each chunk must be self-contained enough to answer a question on its own — the Synthesizer deliberately keeps chunks semantically tight so generated questions do not require cross-chunk reasoning.
  3. Fact extraction stage (optional): Some Synthesizer configurations first extract key facts or themes from each chunk, ensuring generated questions are anchored to concrete, verifiable content rather than vague impressions of the passage.
  4. Question generation stage: For each chunk, the LLM generates one or more candidate questions whose answers are derivable from that chunk alone. The Synthesizer controls quantity, difficulty, and style through configuration — for example, asking for factual questions versus reasoning questions.
  5. Answer generation stage: For each generated question, the LLM produces the ideal answer strictly from the chunk. Because the answer is generated from the same chunk that will be recorded as reference context, the golden is internally consistent by construction.
  6. Context attachment stage: The chunk that produced the question-answer pair is attached to the golden as its reference context. This is the anchor that makes the golden useful for RAG evaluation — the metric can compare generated answers against the same context a real retriever would have supplied.
  7. Filtering stage: The Synthesizer applies quality filters. Questions that are too vague, too similar to already-generated examples, or whose answers cannot be verified against the chunk are dropped. This improves the discriminative power of the final dataset — a smaller, cleaner set is better than a larger, noisier one.
  8. Persistence stage: The surviving triples — (input, expected_output, reference_context) — are stored as goldens in a dataset, ready to be evaluated against the application.
Internal Quality Guard: The Synthesizer's filtering stage is what separates a usable dataset from a noisy one. Without filtering, LLM-generated questions often cluster in the same style, cover the same few facts repeatedly, and produce answers that leak beyond the source chunk. The filter is the safety net that keeps the dataset well-formed.

9.4 Internal Components of the Synthesizer

Internally, the Synthesizer is composed of several cooperating sub-components. Each one has a narrow job, and together they build a dataset that is both high-coverage and high-fidelity to the source material.

Sub-ComponentJob
Document LoaderParses PDFs, text, and web pages into raw text plus metadata such as source filename or page.
ChunkerSplits long documents into overlapping passages sized to fit comfortably in the judge LLM's context window.
Fact ExtractorPulls out concrete, verifiable facts per chunk so that generated questions are anchored to real content.
Question GeneratorProduces close-ended or open-ended questions whose answers live entirely within a single chunk.
Answer GeneratorProduces the ideal answer using only the same chunk as reference — guaranteeing the golden is internally consistent.
EvolverOptionally transforms a golden into harder variants — reasoning-heavy, multi-step, or adversarially worded — to raise dataset difficulty.
Filter / DeduplicatorDrops near-duplicates, ambiguous questions, and unverifiable answers to keep the dataset clean.

9.5 Evolver — How Difficulty Is Raised Internally

The Synthesizer's Evolver step is one of the most distinctive parts of the internal pipeline. Rather than generating all questions at the same difficulty level, the Evolver takes a base golden and transforms it into harder variants:

  • Reasoning evolution: Convert a factual question into one that requires combining facts or performing inference.
  • Multi-context evolution: Rewrite a single-chunk question so its answer requires synthesising multiple chunks.
  • Conditional evolution: Add constraints to the question so that the correct answer depends on satisfying a condition.
  • Distractor evolution: Introduce plausible but incorrect alternative answers so the model must discriminate, not just recognise.

Evolved goldens stress-test the application harder than base goldens — a system that performs well on both has strong coverage across difficulty levels.

9.6 Golden Formation — Internal Quality Principles

  • Anchoring principle: Every golden's expected output is anchored to a specific reference context. Change the source document and the golden must be regenerated or it becomes stale.
  • Self-consistency principle: Because the answer is generated from the same chunk that is stored as context, the golden is internally consistent by construction — no accidental mismatch.
  • Coverage principle: The Synthesizer aims to cover the source's key facts and themes rather than sampling randomly. Coverage is a configuration knob, not an accident.
  • Diversity principle: Question phrasings and styles are deliberately varied to prevent the dataset from being biased toward a single template.
  • Filtering principle: Quality filtering is a first-class stage, not an afterthought. A clean small dataset beats a noisy large one for regression detection.
Key Internal Insight: A synthesized golden is really a mini-review of the source chunk. The chunk posed the question implicitly; the Synthesizer made it explicit; the answer is what a careful reader would say. This is why synthesized datasets are surprisingly robust — the ground truth is not invented, it is extracted.

9.7 Dataset Formation — From Goldens to a Runnable Benchmark

Goldens alone are not a dataset. Dataset formation is the step that turns a pile of goldens into a runnable benchmark by attaching the context required to evaluate the application against them.

  1. Golden collection: All goldens produced by the Synthesizer are gathered into a single store.
  2. Deduplication: Near-identical goldens are collapsed to avoid inflating scores with repeated examples.
  3. Field completion: Fields required by the chosen metrics are populated — input, expected_output, and reference_context are always set; others as needed.
  4. Optional partitioning: Some workflows split goldens into training/validation/test partitions, though for evaluation most teams keep a single fixed test set that is reused every run.
  5. Version anchoring: The dataset is tied to a specific source-document version. When sources change, the dataset is versioned accordingly, so regressions can be attributed correctly.
Why versioning matters: If you change the source documents but do not regenerate the goldens, metrics that compare against expected_output will show degraded scores for reasons unrelated to your application. Always version goldens alongside their source material.

10. How Evaluation Is Done Using DeepEval — End to End

This section walks through the full evaluation workflow — from the moment you have an application to the moment you have a pass/fail signal you can act on. It connects every earlier concept: goldens, test cases, metrics, the judge, and thresholds.

10.1 Phase 1 — Prepare the Benchmark

  1. Decide what to evaluate: Identify the properties that matter for your application — correctness, faithfulness, safety, agentic behaviour, or a mix.
  2. Choose metrics: Select the specific metrics whose failure modes would indicate a real problem. Avoid selecting every metric "just in case" — each metric adds a judge call, latency, and its own noise.
  3. Build or synthesize the dataset: If you have goldens, load them. If not, run the Synthesizer over source documents to create them. In either case, verify the dataset is well-formed — every golden must have input, expected_output, and reference_context populated.

10.2 Phase 2 — Produce Test Cases

  1. Run the application on each golden's input: The application under test — a RAG pipeline, an agent, a chatbot — receives each golden's input and produces its actual output, retrieved context, and (for agents) the tools called.
  2. Package the results into test cases: Each application run becomes a test case carrying the golden's expected fields alongside the application's actual fields. This is what metrics will consume.
  3. Optionally check reference baseline: Running the metrics against the golden's own expected_output as the actual_output produces a ceiling score — the maximum the metrics can award. Comparing the ceiling to the application's score tells you how much headroom exists.

10.3 Phase 3 — Execute the Metrics

  1. Select judge model: The judge model is the LLM that will be invoked internally by every LLM-based metric. Choose one that is at least as capable as the model under test.
  2. Run each metric against each test case: For each (test case, metric) pair, the metric executes its internal pipeline — preprocessing, judge invocation, parsing, scoring, reason extraction.
  3. Handle retries: If the judge returns a malformed response, the metric retries up to a configured limit. If retries are exhausted, the metric records a failure with a diagnostic reason — not a silent zero.
  4. Record self-explanation: Alongside the numeric score, the metric's natural-language reason is stored. This is used later when you inspect which specific claims failed and why.

10.4 Phase 4 — Aggregate and Gate

  1. Compare scores to thresholds: Each (test case, metric) pair's score is compared to the metric's threshold. Pairs below threshold (or above, for reverse-scaled metrics) are marked as failures.
  2. Aggregate across the dataset: Per-metric aggregates are computed — mean score, median score, pass rate, and worst-performing cases. These give you the shape of the evaluation, not just a single number.
  3. Identify failure clusters: Failing cases are inspected in groups. Patterns often emerge — for example, all Faithfulness failures involve claims about a specific document section, or all Answer Relevancy failures involve a particular type of query.
  4. Gate the deployment: In CI, a suite that fails its gate blocks the build. In local runs, the gate is a signal for whether to iterate before shipping.

10.5 Phase 5 — Iterate and Track

  1. Fix root causes: Use the failure clusters to trace back to the underlying cause — a retriever issue, a prompt issue, a chunking issue, or an LLM capability issue.
  2. Re-run against the same dataset: Because the dataset is fixed and versioned, comparisons across iterations are meaningful. Score changes reflect actual application changes, not test-set changes.
  3. Expand the dataset as you learn: Whenever you fix a real failure, add a golden covering that failure mode. The dataset becomes an institutional memory of everything the application has ever broken.
  4. Track trends: Over time, aggregate scores trend either upward (healthy iteration) or downward (accruing regression). Trends are the earliest signal of a problem, well before users notice.
🧠 Memory Hook: Benchmark → Test Cases → Metrics → Judge → Score + Reason → Threshold → Report → Fix → Repeat. This loop never ends — it is the heartbeat of a production LLM application.

11. RAG Metrics — Internal Mechanics

11.1 Faithfulness

Internal pattern: QAG with a contradiction test against retrieval_context. The metric decomposes actual_output into atomic claims, then asks whether each claim contradicts anything in the retrieved context. A claim that neither appears in nor contradicts the context is scored as truthful — the failure condition is active contradiction, not mere silence.

Faithfulness — Internal Ratio
$$ \text{Faithfulness} = \frac{\text{Claims NOT Contradicting Context}}{\text{Total Claims Extracted}} $$
Claims = atomic units extracted from actual_output
Truthful = claim does not contradict anything in retrieval_context
Higher is better — 1.0 means every claim is consistent

11.2 Answer Relevancy

Internal pattern: QAG with a relevance test. Decomposes actual_output into statements, then asks whether each statement addresses the input. Off-topic padding lowers the score.

Answer Relevancy — Internal Ratio
$$ \text{Answer Relevancy} = \frac{\text{Relevant Statements}}{\text{Total Statements}} $$

11.3 Hallucination — The Reverse-Scaled Metric

Internal pattern: QAG with a contradiction test against a curated context, not the retriever's output. This metric is phrased as an error rate, so lower is better.

Hallucination — Internal Ratio
$$ \text{Hallucination} = \frac{\text{Contexts Contradicted}}{\text{Total Contexts}} $$
Lower is better — 0 = no contradictions (best possible)
Threshold here is a MAXIMUM, not a minimum
Context field = curated reference material, NOT retrieval_context
Faithfulness vs Hallucination Internally: Both use QAG with contradiction checking, but they read different fields. Faithfulness reads retrieval_context (the retriever's live output). Hallucination reads context (a curated reference). Use Faithfulness for live RAG; use Hallucination for a fixed reference document.

11.4 Contextual Precision, Recall, and Relevancy (Retriever-Side)

MetricInternal Question It AsksFields Read
Contextual PrecisionAre relevant chunks ranked above irrelevant ones?input, retrieval_context, expected_output
Contextual RecallDo retrieved chunks contain everything needed to produce the expected output?input, retrieval_context, expected_output
Contextual RelevancyIs the retrieved context on-topic for the input, regardless of rank?input, retrieval_context

11.5 Summarization — The Min-of-Two Score

Internal pattern: Two QAG sub-evaluations combined via minimum. The metric computes an alignment score (is the summary faithful to the source?) and an inclusion score (does the summary cover the source's key facts?). Final score is the smaller — the summary must excel at both to score high.

Summarization — Internal Combination
$$ \text{Summarization} = \min(\text{Alignment}, \text{Inclusion}) $$
Alignment = fraction of summary claims supported by source
Inclusion = fraction of source facts present in summary

13. Conversational Metrics — Internal Mechanics

Conversational metrics operate over a whole thread of turns rather than a single interaction. Internally, the metric receives the sequence of turns as a single unit and judges properties that only make sense across the whole conversation.

MetricWhat It Internally Judges
Conversation CompletenessAcross the full thread, did the assistant satisfy every user request raised so far?
Conversation RelevancyGiven the accumulated context up to each turn, was the reply on-topic at that moment?
Knowledge RetentionDoes the assistant carry forward and correctly reuse facts stated earlier in the thread?
Role AdherenceDoes the assistant stay within its assigned persona across all turns without drifting?

14. Safety / Red-Teaming Metrics — Internal Mechanics

Safety metrics judge the output against predefined harm categories. Internally, most of these are G-Eval-based — the judge receives a rubric describing the harm category and scores the output's alignment with that rubric.

MetricWhat It Internally Judges
BiasPresence of biased language, stereotyping, or unfair generalisations
ToxicityPresence of toxic, offensive, or hateful content
Prompt AlignmentWhether the output followed the explicit instructions given in the prompt
Red-Teaming VulnerabilitiesResistance to jailbreaks, prompt injection, and data leakage — tested with adversarial inputs

18. Exam Cram Facts

  • DeepEval internally layers into data, metric, judge, reasoning, synthesizer, orchestration, and reporting.
  • Three internal reasoning techniques power almost all metrics: QAG (ratio of countable judgments), G-Eval (rubric + CoT + token-probability weighting), DAG (deterministic decision graph).
  • QAG has four stages: decomposition → question generation → answering → aggregation into a ratio.
  • G-Eval scores via a probability-weighted sum across a rating scale — reduces variance.
  • DAG forces multi-condition rubrics into a graph of single-purpose decisions with explicit branching.
  • Synthesizer has three modes: from documents, from existing goldens, from scratch.
  • Synthesizer pipeline: Ingest → Chunk → Extract Facts → Generate Questions → Generate Answers → Attach Context → Filter → Persist.
  • Synthesizer's Evolver raises difficulty via reasoning, multi-context, conditional, and distractor evolutions.
  • Every golden is anchored to a reference context. Change sources → regenerate goldens.
  • Evaluation phases: Prepare benchmark → Produce test cases → Execute metrics → Aggregate and gate → Iterate and track.
  • Faithfulness = QAG contradiction test against retrieval_context (higher better).
  • Answer Relevancy = QAG relevance test against input.
  • Hallucination = QAG contradiction test against curated context — reverse-scaled (lower better).
  • Summarization = min(alignment, inclusion) — must be faithful AND comprehensive.
  • Tool Correctness = deterministic comparison; Task Completion = LLM-judged outcome.
  • Every metric is self-explaining — always returns a score AND a reason.

9Difference between Faithfulness and Hallucination metrics?Faithfulness checks against retrieval_context (live RAG retriever output); Hallucination checks against a curated, trusted context and is reverse-scaled (lower = better).
10How is the Summarization score computed?The minimum of the alignment score (factual consistency) and inclusion score (comprehensiveness) — both must be strong.
11What's the difference between ToolCorrectnessMetric and TaskCompletionMetric?Tool Correctness deterministically compares called vs expected tools; Task Completion uses an LLM judge to assess whether the goal was achieved.
12Why is versioning the dataset important?Goldens are anchored to a source-document version. Versioning lets you attribute score changes to application changes rather than dataset changes.
