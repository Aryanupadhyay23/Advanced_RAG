Vector Stores & ANN

Efficient storage and retrieval of high‑dimensional vectors – brute‑force, HNSW, IVF centroid‑based, and CRUD operations.

1. Core Idea

  • What is a Vector Store? A specialized database optimized to store, index, and search high‑dimensional vectors (embeddings) using similarity metrics (cosine, dot product, Euclidean). It’s the backbone of semantic search and RAG systems.
  • Why do we need it? When you have millions of document chunks, linear brute‑force scan is too slow. Vector stores implement Approximate Nearest Neighbour (ANN) algorithms that trade a tiny amount of accuracy for massive speedups.
  • Key techniques: Brute‑force (exact, slow), HNSW (graph‑based, fast, memory‑intensive), IVF (clustering + inverted files, balanced), and many others (PQ, DiskANN).
  • CRUD: Vector stores support Create (insert), Read (search), Update (modify vectors/metadata), and Delete (remove vectors) – essential for dynamic, real‑world applications.

2. Brute‑Force (Exact) Search

  • How it works: For a query vector $\mathbf{q}$, compute the similarity (e.g., cosine) between $\mathbf{q}$ and every stored vector $\mathbf{v}_i$. Sort all results and return the top‑$k$.
  • Complexity: $O(N \cdot d)$ per query, where $N$ = number of vectors, $d$ = dimension. Linear in $N$.
  • Pros: Always returns the exact top‑$k$ (perfect recall). No index build time.
  • Cons: Infeasible for large $N$ (millions) – latency grows linearly. Memory‑intensive if all vectors must be loaded.
  • When to use: Small datasets (< 10k vectors), benchmarking, or when 100% recall is mandatory and latency is not a concern.

3. HNSW – Graph‑Based ANN

3.1 Intuition

Imagine a multi‑layer graph. The top layer has few nodes (long‑range connections). Lower layers add more nodes and finer‑grained connections. Search starts at the top and greedily moves to the nearest neighbour, descending to lower layers for refinement.

3.2 How it Works

  • Index building: Insert vectors one by one. For each new vector, connect it to its $M$ nearest neighbours at each layer. The probability of a vector appearing in a higher layer is $1/\text{ml}$ (scaling factor).
  • Search: Start at an entry point in the top layer. Greedily move to the closest neighbour until no closer neighbour is found. Descend one layer, repeat. At the bottom layer, collect top‑$k$ using a candidate list.
  • Key parameters: $M$ (max connections per node, typical 16‑64), efConstruction (beam width during build, typical 200‑500), efSearch (beam width during query, larger → higher accuracy but slower).
  • Complexity: Search approx $O(\log N)$. Build time $O(N \log N)$.
  • Memory: Stores the full graph: $O(N \cdot M)$ edges. High memory footprint for large $N$.

3.3 Pros & Cons

  • ✅ Fast: Sub‑linear query time, very high recall (> 99%) with proper tuning.
  • ✅ Incremental: Supports insertion without full rebuild.
  • ❌ Memory hungry: Graph storage can be several times the raw vectors.
  • ❌ Build time: Construction is slower than some alternatives, especially for high $M$ and $efConstruction$.

4. IVF – Inverted File with Clustering

4.1 Intuition

First, partition the vector space into clusters (e.g., using k‑means). For each cluster, store a centroid and an inverted list (posting list) of all vectors belonging to that cluster. At query time, only probe the nearest centroids and search within those lists.

4.2 How it Works

  • Index building: Run $k$‑means on a training set of vectors to obtain nlist centroids (e.g., 4096). For each vector in the dataset, find its nearest centroid and append the vector (or its ID) to that cluster’s inverted list.
  • Search: Compute distances between the query and all centroids. Select the top nprobe clusters (e.g., 10). Perform brute‑force or another ANN method within those clusters only.
  • Key parameters: nlist (number of clusters, larger → finer granularity, but overhead), nprobe (number of clusters to probe during search, higher → more accurate but slower).
  • Complexity: Search time proportional to $(\text{nprobe} / \text{nlist}) \cdot N$ on average. With large $N$ and small $\text{nprobe}$, huge speedup.
  • Memory: Stores only the centroid + inverted lists (vectors themselves). Often combined with Product Quantization (IVF‑PQ) to compress vectors and reduce memory further.

4.3 Pros & Cons

  • ✅ Scalable: Handles billions of vectors when combined with PQ.
  • ✅ Memory efficient (with PQ): Compressed vectors reduce storage drastically.
  • ✅ Tunable: nprobe gives direct speed/accuracy trade‑off.
  • ❌ Requires training: Must pre‑train k‑means centroids (offline).
  • ❌ Less adaptive: Cluster sizes can become skewed; some clusters may be heavily probed.

6. CRUD Operations in Vector Stores

OperationDescriptionExamples / Notes
Create (Insert)Add new vectors with an ID and optional metadata (e.g., source, page). For ANN indexes, vectors are inserted into the graph (HNSW) or assigned to a cluster (IVF).add(vectors, ids, metadata)
Read (Query / Search)Given a query vector and top‑$k$, return the $k$ most similar vectors (with scores and metadata). Supports metadata filtering (pre‑ or post‑filtering).search(query_vector, k=5, filter={"category": "sports"})
UpdateModify the embedding vector and/or metadata of an existing document. Often implemented as a delete + re‑insert. HNSW may rebuild local connections.Update metadata: in‑place if storage supports it. Update vector: re‑index.
DeleteRemove a vector by its ID or by a metadata filter. In HNSW, neighbor links must be repaired; in IVF, the vector is removed from the inverted list.delete(ids=["id1", "id2"]) or delete(filter={"date": {"$lt": "2023-01-01"}})

6.1 Metadata & Filtering

  • Pre‑filtering: Apply metadata filter before ANN search. Works well if the filter is very selective; otherwise, may scan too many vectors.
  • Post‑filtering: Retrieve top‑$k'$ ($k' > k$) candidates via ANN, then apply metadata filter. Ensures $k$ results but may miss relevant vectors if the filter eliminates many candidates.
  • Best practice: Use a hybrid approach or tune $k'$ according to filter selectivity.

7. Why Vector Stores Matter

  • Fast retrieval: Sub‑100ms response times even with millions of documents, essential for interactive LLM applications.
  • Scalability: Horizontal scaling and cloud‑native designs (Pinecone, Weaviate) handle growing data without degrading performance.
  • Flexible metadata: Combine semantic search with structured filters (e.g., date, author, category) for precise results.
  • Integration: Plugs directly into RAG pipelines: embed → insert; query → search → augment prompt → generate.
  • Persistence: Data survives restarts; allows incremental indexing and real‑time updates.

8. Interview Questions

Q1: Why can’t we just use brute‑force search for all retrieval tasks?

A: Brute‑force scales linearly with the number of vectors ($O(N)$). For millions of vectors, latency becomes unacceptable (e.g., hundreds of milliseconds or more). ANN methods trade a tiny accuracy loss for orders‑of‑magnitude speedup.

Q2: Explain how HNSW achieves fast search. What are its key parameters?

A: HNSW builds a multi‑layer graph where each node connects to its $M$ nearest neighbours. Search starts at the top layer and greedily descends. Parameters: $M$ (connections per node), efConstruction (build quality), efSearch (search quality). Higher values improve recall at the cost of speed and memory.

Q3: Describe the IVF algorithm and how it uses centroids.

A: IVF runs k‑means on training vectors to obtain nlist centroids. Each vector is assigned to its nearest centroid, forming an inverted list per cluster. At query time, only the top nprobe closest clusters are searched. It’s very memory‑efficient when combined with PQ.

Q4: How do vector stores handle CRUD operations while maintaining search accuracy?

A: Insertions add vectors to the index (HNSW adds nodes and edges; IVF assigns to clusters). Deletions mark vectors as removed and may require periodic index maintenance. Updates often delete and re‑insert. Metadata is typically stored separately and used for filtering during search.

Q5: What is the difference between pre‑filtering and post‑filtering in a vector search?

A: Pre‑filtering reduces the search space to vectors matching a metadata filter before ANN, which can be efficient if the filter is selective. Post‑filtering retrieves a larger candidate set via ANN and then applies the metadata filter; it guarantees $k$ results but may miss vectors if the candidate set doesn’t include them. Hybrid tuning is often needed.

9. Common Mistakes

❌ Wrong Belief✅ Correct Understanding
"ANN returns exactly the same results as brute‑force."ANN is approximate; it may miss the true nearest neighbours. Recall can be tuned but is never 100% guaranteed.
"HNSW works out‑of‑the‑box without tuning."Parameters like $M$ and efSearch heavily influence recall and latency; they must be tuned per dataset and performance target.
"IVF can be used without training."IVF requires k‑means training (offline) to build centroids. Without training, it cannot partition the space.
"Vector stores are only for retrieval; they can't filter by metadata."Modern vector stores support rich metadata filtering alongside vector search, enabling hybrid queries.
"Once a vector is inserted, it can never be updated."While some stores prefer immutable vectors, most support updates (via delete+insert) and metadata modifications.

10. Exam Cram Facts (Day‑Before Revision)

  1. Vector stores index high‑dimensional vectors and support similarity search at scale.
  2. Brute‑force: $O(N \cdot d)$, 100% recall, only for small $N$.
  3. HNSW: multi‑layer graph, parameters $M$, efConstruction, efSearch. Fast, high recall, memory‑intensive.
  4. IVF: k‑means clustering, inverted lists. Parameters: nlist, nprobe. Scalable, memory‑efficient with PQ.
  5. CRUD: Create (insert vector + metadata), Read (ANN search + metadata filter), Update (often delete+insert), Delete (remove by ID/filter).
  6. Filtering: pre‑filtering (filter then search), post‑filtering (search then filter). Choose based on selectivity.
  7. ANN trades a tiny accuracy loss (recall ~99%) for 10‑1000× speedup over brute‑force.
  8. Popular vector stores: Pinecone, Weaviate, Milvus, Qdrant, Chroma, FAISS (library).
  9. RAG pipeline: query → embed → ANN search → retrieve chunks → augment prompt → generate.
